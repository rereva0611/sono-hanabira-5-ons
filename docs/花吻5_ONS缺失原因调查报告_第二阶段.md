**只写新增发现。第一阶段已确立的背景（缺 5 现象、FJSYS、可解包、VNDS/Ren'Py 有 5、"版权说"错误、ONS 生态衰落）不再重复。**
调查日期：2026-09-16｜证据分级：**A**=直接证据（源码/README/本人原话）｜**B**=强技术证据｜**C**=强历史推断｜**D**=普通推测

## 1. 本轮最重要的新发现

1. **【A】Proger 的 `msd_3` 之谜彻底解决，答案是"其他含义"。** 三个工具是**同一个程序的三个编译**，唯一差别是一个常量 `h0`（MD5 密钥种子）。`msd_1` 的 `h0` = `その花びらにくちづけを`（第1作标题），`msd_2` = `その花びらにくちづけを　わたしの王子さま`（第2作），**`msd_3` = `その花びらにくちづけを　あなたを好きな幸せ`（第5作）**。Proger 写的 "1/2/3" 是**编译序号**，不是作品序号。
2. **【A】FJSYS 的 MSD 加密密钥 = 该作自己的日文标题字符串（Shift-JIS）。** 因此**不存在"某一作密钥拿不到"的可能**——密钥不是秘密，只要知道标题就能推导。这把"第5作卡在密钥"整类解释从根上排除。
3. **【A】ArcTool 的 FJSys 插件里有一张 19 款游戏 × 19 个密钥的对照表**，`(5) Anata wo Sukina Shiawase → その花びらにくちづけを　あなたを好きな幸せ` 赫然在列（第 4 号索引，紧邻第4、第6作）。同表的 `(?) Anata ni Chikau Ai` 条目用的是**半角空格**而其余用全角空格——这正是 Proger 反复"修正加密密钥"的真实原因。
4. **【A】ArcTool 能封包。** `TFJSysArc.Capabilities = ARC_READ or ARC_WRITE`。**这修正了第一阶段的结论**：不是"没有工具能重新封包"，而是"GARbro 不能，ArcTool 能"。2011-05 的 readme 已宣称 ArcTool "supports all 8 Sono Hanabira games"。
5. **【A】PSP 版同样缺第 5 作**，而且比 ONS 更早被记录。2010-09-14 的移植进度原帖逐作列表里，**"5.還沒有人做"**，而 1–4 均有人认领。
6. **【A】找到一次有移植者本人说明原因的弃坑**（花吻3 PSP），原因不是技术，而是**汉化组授权协商失败**。
7. **【A】汉化组授权机制被坐实**：花吻系列是"合作汉化"，无单一授权主体；花吻2 的组"不允许"移植，花吻1"不是曙光汉化的所以管不着"。
8. **【A】"第5作缺中文文本"被否证**：2010-01-24 的贴吧帖《花吻在上1-5中文版》已列出 `花吻5-爱上你的幸福.rar`（rayfile 链接，GUID 时间戳约 2009-11）。
9. **【C】ONS 1–3 与 7–10 出自同一批素材池**：2025 年贴吧反馈指出"移植版 1-3 作使用了后面 7-10 作的 ed"，且选项判定被改写（PC 版 75% 通关 → 移植版 100%）。这是"人工重写 + 同一批人/同一模板"的指纹。
10. **【B】VNDS 不是一次性统一转换，且第5作包内没有独立的选择支脚本**（修正第一阶段"VNDS5 含选择支"的推断）。未找到任何 FJSYS→VNDS 转换器。

## 2. Proger `msd_3` 歧义：最终判定

### 2.1 判定结果：**C —— 其他含义**

`msd_1 / msd_2 / msd_3` **既不是"三部作品的三个版本"，也不是"三代 FJSYS/MSD 格式"**，而是：

> **同一个控制台程序的三个编译版本，唯一差异是源码里的一个常量 `h0`。**

三个 `.dpr` 的程序体（文件表读取、条目替换、增量偏移修正、`MSCENARIO FILE  ` 未加密判定、XOR 解密循环）**逐行相同**，只有 `const h0` 一行不同。

### 2.2 源码原文（字节级验证）

| 工具 | `h0` 原始字节（SJIS） | 解码结果 | 对应作品 |
|---|---|---|---|
| `msd_1` | `82bb82cc89d482d182e782c982ad82bf82c382af82f0` | `その花びらにくちづけを` | 第 1 作 |
| `msd_2` | `…82f0 8140 82ed82bd82b582cc89a48e7182b382dc` | `その花びらにくちづけを　わたしの王子さま` | 第 2 作 |
| **`msd_3`** | `…82f0 8140 82a082c882bd82f08d4482ab82c88d4b82b9` | **`その花びらにくちづけを　あなたを好きな幸せ`** | **第 5 作** |

`msd_1.dpr` 第 21 行还自带注释：

```pascal
const
  // starting point for MD5 hashes
  h0 = '偦偺壴傃傜偵偔偪偯偗傪'; // it says 'Sono Hanabira ni Kuchizuke wo'
```

（显示为 `偦偺…` 是 Shift-JIS 字节被按 GBK 解读的乱码；按 cp932 解码即为 `その花びらにくちづけを`。）

### 2.3 为什么 "3" 是编译序号而不是作品序号

同一作者在 ArcTool 的 `FJSysArc.pas` 里写的密钥表，**是按发售顺序编号的，且把 好きな幸せ 编为 (5)**：

```pascal
EncryptedGamesList = '(1) Sono Hanabira ni Kuchiduke wo|(2) Watashi no Ouji-sama'
                   + '|(3) Anata to Koibito Tsunagi|(4) Itoshisa no Photograph'
                   + '|(5) Anata wo Sukina Shiawase|(6) Kuchibiru to Kiss de Tsubuyaite' …
GamesKeys: array[0..18] of String = (
    'その花びらにくちづけを',                              // (1)
    'その花びらにくちづけを　わたしの王子さま',              // (2)
    'その花びらにくちづけを　あなたと恋人つなぎ',            // (3)
    'その花びらにくちづけを　愛しさのフォトグラフ',          // (4)
    'その花びらにくちづけを　あなたを好きな幸せ',            // (5)  ← 第5作
    … );
```

**他知道 好きな幸せ 是第 5 作。** 因此 2009 年那条 changelog 里的 "3" 只能是编译序号。

### 2.4 加密算法（两处独立实现完全一致）

```pascal
Hash := LowerCase(MD5DigestToStr(MD5String(FHash + IntToStr(Chunk))));
Buf[I] := Char(Byte(Buf[I]) xor Byte(Hash[I mod 32 + 1]));
```

即：**密钥流 = 小写十六进制 MD5(密钥种子 + 分块序号)，按 32 字节分块 XOR**。与 GARbro `ArcFJSYS.cs` 的 `MsdTransform` 完全吻合。若条目以 ASCII `MSCENARIO FILE  ` 开头，则视为未加密、跳过解密。

### 2.5 判定带来的最重要后果

> **密钥种子就是作品自己的日文标题。** 这意味着：
> - 任何知道游戏名的人都能推导出密钥，**不需要从任何人那里"拿到"密钥**；
> - Proger 反复"修正加密密钥"，修的是**标题字符串的空格写法**（全角 U+3000 还是半角空格、有没有多余尾随空格）——`Checklist.txt` 里就明确写着 `key: その花びらにくちづけを あなたに誓う愛`（半角），而表里其它条目用全角；
> - **Proger 在 2009-09-22 就发布了一个可用的第 5 作专用工具**，比 PSP 的 8 款名单（2013）早 4 年，比 ONS 套件早得多。

## 9. 新的因果模型

> 按用户要求：不评分、不强行选赢家。每条列出支持证据、反对证据、还缺什么证据。

### 模型 A：技术障碍（密钥 / 格式 / 工具）

- **支持证据**：FJSYS 的 MSD 确实按作品加密（`ArcFJSYS.cs`）；字符集/心形符号确实在第 3–4 作附近变化过（ArcTool changelog）。
- **反对证据（压倒性）**：密钥 = 作品自己的标题（A 级源码）；`msd_3` 在 **2009-09-22** 就是第 5 作专用工具（A 级）；ArcTool 密钥表含 `(5)`（A 级）；2011-05 已"supports all 8"（A 级）；FJSYS 格式对 1–12 统一、解析器无按作品分支（A 级）；VNDS 与 Ren'Py 都能承载第 5 作。
- **还缺什么**：PC4/PC5/PC6 的实际命令集差分（无样本，未做）。但即使做出来，也很难解释"为什么 6 有 ONS 而 5 没有"。
- **判定：基本被排除。**

### 模型 B：汉化文本上游障碍

- **支持证据**：**汉化组授权确为真实关卡，且已导致一次弃坑**（花吻3 PSP，A 级）；汉化是"合作汉化"，无单一授权主体（A 级）；花吻2 的组"不允许"、花吻1"管不着"（A 级）；花吻16 的 ONS 移植者 2015 年仍要"感谢汉化组的授权"（A 级）。
- **反对证据**：**第 5 作的中文版在 2009-11 就已在流通**（A 级）→ "缺文本"不成立；且已获授权的/自行移植的案例（花吻1、2 都"在没有允许的情况下自行移植了"）说明授权并非绝对阻碍。
- **还缺什么**：第 5 作汉化组的身份，以及该组是否曾拒绝授权移植。**这是本模型唯一的、也是最关键的缺口。**
- **判定：原始表述被否证；授权变体仍存活，但缺第 5 作的直接证据。**

### 模型 C：同一移植者主动跳过

- **支持证据**：ONS 1–3 与 7–10 同批（C 级指纹）；若为一人按批次作业，"跳过 5"就是主动选择。
- **反对证据**：**找不到任何移植者身份**，因此"主动"无从证明；PSP 线显示 1–4 由**不同人**分别认领（萌動、我、智代、公主），并非一人连续作业 → 同一逻辑下 ONS 也未必是一人。
- **还缺什么**：ONS 套件的移植者 ID，以及任何"我跳过了 5"的自述。
- **判定：无法判断。**

### 模型 D：不同移植者造成的偶然缺口（协调缺口）

- **支持证据（本轮最强的新证据）**：**2010-09-14 的 PSP 进度帖逐作列出：1 有人、2 有人、3 有人（未发布）、4 有人、5 "還沒有人做"，而 6 已"據說有"** → **5 是 1–5 序列里唯一无人认领的一作，且社区注意力已越过它转向 6**；同帖 牧濑红莉栖 说"其实俺可以去弄的…不过某些原因…"；PSP 最终产出 1/2/3/4/6/7/8 而永缺 5；ONS 线的覆盖范围与 PSP 高度重合且同样缺 5。
- **反对证据**：这只解释了"2010 年那一刻 5 没人做"，**不能解释"此后 15 年无人回头补"**；也不能解释为什么偏偏是 5 而不是 4。
- **还缺什么**：ONS 线的作业顺序记录；以及"是否曾有人回头尝试补 5"的任何痕迹。
- **判定：目前证据最扎实，但只解释了缺口的**起源**，未解释其**延续**。**

### 模型 E：ONS5 存在但未进入公开合集

- **支持证据**：ONS 资源长期靠网盘/QQ 私传，公开索引天然不完整；ONS 套件本身存在"同作多版本"（花吻1 两份、花吻4 两份且体积不同），说明套件有反复重打包史；2025 年仍有人在贴吧称"有"并私发 QQ。
- **反对证据**：**在本次查到的所有索引中零痕迹**——包括一个 189 条的 ONS 合集、一个 6,948 路径的大归档、8 年间所有相关贴吧讨论，**没有任何一次出现"花吻5 ONS"的文件名、截图或发布帖**。若曾公开存在，8 年不可能一次都没被引用。
- **还缺什么**：任何 ONS5 文件、截图、发布帖或存档快照。QQ 私聊分发在技术上不可追溯。
- **判定：低可能，但不能完全排除。**

### 模型 F（补充，用户未列）：缺口是"中文掌机线"共有，而非 ONS 独有

- **支持证据**：PSP 与 ONS 都缺 5，且都含 1/2/3/4/6/7/8（A 级）；非中文线（VNDS 1–8）与 Ren'Py 线都有 5（A 级）。
- **反对证据**：ONS 另有 9/10/12 而 PSP 没有 → 两条线并非完全同源。
- **还缺什么**：两条线的脚本是否存在继承关系（AMP→ONS 在机制上不太可能，但"同一批人、同一素材池"是可能的）。
- **判定：这一模型把问题从"ONS 为什么缺 5"正确地改写为"中文掌机移植线为什么缺 5"。**

## 11. 当前最接近真相的解释

### 11.1 已确证的事实链（可直接引用）

1. **第 5 作不存在任何技术独特性**：密钥 = 自己的标题（可推导），专用工具 2009-09-22 即已存在，ArcTool 密钥表含 `(5)`，2011-05 已覆盖 1–8，格式对全系列统一，GARbro/ArcTool/FJSYS-Extractor 均可处理。
2. **第 5 作的中文文本不是障碍**：2009 年底～2010 年初已公开流通。
3. **缺口不是 ONS 独有**：PSP 版同样缺 5，且 2010-09-14 就有"5.還沒有人做"的同期记录。
4. **中文掌机移植线受制于汉化组授权**，并已产生一次有移植者本人说明原因的弃坑（花吻3）。
5. **ONS 套件 1–3 与 7–10 出自同一批处理流程**（ED 复用 + 选项逻辑改写），且是人工重写而非自动转换。

### 11.2 目前最站得住的叙述

> 缺口的**起源**可以定位到一个具体时点：**2010 年 9 月 14 日**，中文掌机（PSP）移植线上，1–4 均已有人认领、**唯独第 5 作无人认领**，而社区的注意力已经越过它转向第 6 作。这条线当时正被汉化组授权问题反复绊倒（两个月前刚有一次弃坑），产出本就零散、由不同人分头认领。此后 ONS 线继承了大致相同的覆盖范围（同样缺 5），而两条线都没有人回头补第 5 作。

### 11.3 但必须明确写出：**目前仍不能解释"为什么偏偏是 5"**

具体地说，以下问题本轮**没有**得到回答：

- 为什么被跳过的是第 5 作，而不是第 4 作或第 6 作？
- 2010 年之后 15 年间，为什么没有人回头补第 5 作（而 9/10/12 后来却被补上了）？
- ONS 1–4、6–10 的移植者到底是谁？（这直接决定了"为什么从 4 跳到 6"能否回答）

**本报告不把"只是没人做"当作最终答案**——它目前只是"技术类解释被逐条排除后的剩余项"，而不是被正面证实的结论。
